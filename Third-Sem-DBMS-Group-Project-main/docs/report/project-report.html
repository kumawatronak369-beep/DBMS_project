1Introduction

1.1 The problem, in plain words

Every time a computer opens a website or connects to a server, it contacts another machine on the network. Someone who runs a network (a school computer lab, a library, a small office, a home) often needs to answer simple questions: Which computer visited this site? What did this computer connect to yesterday afternoon? Which sites are most used? Answering those questions from raw log files is slow and error prone.

This project solves that. A small program called a collector reports "device X reached destination Y at time T". A backend checks and stores those reports in a database. A web dashboard shows the stored data as tables, charts and reports, with search and filters.

1.2 What it records, and what it never records

Recorded (metadata only)

Which device, which destination IP address, the domain name when known, the time, and optionally the protocol (TCP/UDP) and the two port numbers.

Never recorded

Passwords, cookies, messages, page contents, request or response bodies, packet payloads, keystrokes, or the names of programs.

The system is intended only for networks and devices the operator is authorized to monitor, and whose users know about it. It contains no packet sniffing, scanning or discovery code.

1.3 Who uses it

RoleWhat they can do
ADMINEverything an analyst can do, plus add, edit and disable nodes (observation points), and add, edit and disable user accounts.
ANALYSTRead-only: view the dashboard, nodes, devices, destinations and history, search and filter, and generate reports.
COLLECTORNot a person. A program that can only submit events, using its own API key that belongs to exactly one node.

1.4 Project goals

  • Database design first: a normalized schema with real foreign keys, constraints, indexes and transactions, explained in Section 7.
  • A working, full-stack system: not only a user interface. Real data flows from a collector through an API into MySQL and back out to the browser.
  • Clean architecture: each layer has one job (router, service, repository), so the code is easy to explain and test.
  • Security basics done properly: hashed passwords, token authentication, role checks enforced on the server, and API keys for collectors.

2The big picture

The system has four building blocks that pass data in one direction and answer questions in the other.

Why a separate collector?

A website cannot see your network by itself. Something has to sit at a place that can observe activity and report it. Keeping this as its own small program means the website and database do not change if the data source changes (simulator today, a real data source tomorrow).

Why a backend between the browser and database?

The browser is not trusted. The backend is where logins, roles, validation and business rules are enforced, so nobody can bypass them by editing the web page. The frontend is only a convenience layer.

3The journey of one event

The best way to understand the whole system is to follow one event from start to finish. Imagine the computer PC-LAB-A-001 opens github.com.

3.1 The same journey as a story

  1. The collector notices that PC-LAB-A-001 connected to 203.0.113.20 (github.com) and builds a small JSON message.
  2. It sends the message to POST /api/collector/events with a secret API key in a header.
  3. The backend identifies the caller. It hashes the key (SHA-256) and finds the matching row in collector_api_keys. That row says which node (for example Computer Lab A) the caller belongs to. If the key is unknown or revoked, the answer is 401.
  4. It validates the message. A nodeId in the message is rejected on purpose: a collector must not be able to claim it belongs to a different node.
  5. It resolves the entities. The device is looked up by node + device_identifier and created if new. The destination is looked up by IP + domain and created if new.
  6. It applies the 30-second rule (Section 6). If the same device already reached the same destination within 30 seconds, nothing is stored and the answer is DUPLICATE.
  7. It stores the event in network_history, updates the three last_seen columns and commits the transaction.
  8. The dashboard asks the API for summaries and lists every few seconds, and the new row appears in the tables and charts.

4The collector

The collector is one Python program (collector/collector.py) with several modes. All modes send events through the same API endpoint, so the backend neither knows nor cares which mode produced an event.

4.1 What an event looks like

{
  "deviceIdentifier": "PC-LAB-A-001",
  "deviceIp":        "192.168.10.21",
  "destinationIp":   "203.0.113.20",
  "domain":          "github.com",
  "timestamp":       "2026-09-21T11:08:30",
  "protocol":        "TCP",        // optional
  "sourcePort":      56188,        // optional
  "destinationPort": 443           // optional
}

There is deliberately no node id. The node comes from the API key. Protocol and ports are optional because the simulator and the DNS mode cannot observe them.

4.2 The simulator

Builds events for the seeded demo devices using documentation IP ranges (192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24) that do not belong to real organizations. It deliberately repeats some events so the 30-second rule can be shown live (python collector.py demo-dedup). The dashboard marks demonstration data with a "Demo data" badge.

4.3 The real local TCP collector

On Windows, the operating system keeps a table of every TCP connection. The collector reads it with the built-in IP Helper function GetExtendedTcpTable through Python's standard ctypes. That needs no administrator rights and no extra software (no Npcap, no Scapy).

Important limits

This collector sees only the computer it runs on. It does not monitor other laptops, phones or users on the Wi-Fi, or traffic through a router. It is TCP only: UDP, including the QUIC protocol many browsers use for sites like YouTube, has no connection table, so those visits can be missing. It polls a snapshot, so very short connections can be missed. It provides local TCP connection visibility, not a complete browsing history.

4.4 How the domain name is chosen

A connection table contains only IP addresses. To attach a name, the collector looks in the Windows DNS cache and uses a name only when exactly one cached name maps to that IP address. Large services (CDNs, cloud front ends) share IP addresses between thousands of names, so a single name cannot be chosen honestly; the domain is then left empty (null) rather than guessed. The collector never performs reverse DNS lookups.

5.4 Validation and error handling

  • Pydantic schemas check every incoming value (types, lengths, IP address format, port range 1 to 65535, allowed protocol values). Unknown fields are rejected.
  • Pagination is done by the database (page, pageSize up to 100), so the browser never receives thousands of rows at once.
  • HTTP status codes are meaningful: 200, 201, 204, 400, 401, 403, 404, 409, 422, 503. A 409 means a conflict such as a duplicate node code or an attempt to disable the last administrator.
  • Errors never leak internals. The server logs details but returns generic messages, and it does not echo rejected input back (it could be a password).

6Ingestion and the 30-second rule

A browser loading one page can open many connections to the same server within a few seconds. Storing every one would fill the history with noise. The project's special rule fixes that:

The 30-second rule

Same device + same destination + another event within 30 seconds = duplicate, and a duplicate is not stored. After 30 seconds the same device reaching the same destination is stored again, because that is a new visit.

6.1 Why it lives in the backend, not the database

  • It cannot be a UNIQUE(device_id, destination_id) constraint: that would forbid the same device ever reaching the same destination twice, even a month later.
  • It cannot live in the frontend or collector alone: any client could skip it. The backend is the single place all events pass through, so the rule is enforced once, for everyone.
  • Ports and protocol are not part of the rule. Two connections from one device to one server within 30 seconds are one event, whatever their ports are.

6.2 Making it safe when events arrive at the same time

Two events from the same device could arrive at the same moment and both pass the duplicate check. To prevent that, the service reads with SELECT ... FOR UPDATE (a locking read) and always takes the locks in the same order: node, then device, then destination. A fixed order means two transactions can never wait on each other in a circle (a deadlock). If MySQL still reports a lock timeout, the API answers 503 and the collector simply resends, which is safe because duplicates are detected.

The window is checked in both directions (30 seconds before and after), so an event that arrives late and out of order is also handled correctly.

7The database

The database is the heart of the project. It is a MySQL 8+ (running MySQL 9.7) database named network_monitor with exactly six application tables, all InnoDB, character set utf8mb4, with BIGINT UNSIGNED AUTO_INCREMENT primary keys and DATETIME timestamps.

7.1 Why MySQL and a relational design

  • The data is naturally relational: devices belong to nodes, events refer to devices and destinations. Foreign keys let the database itself guarantee those links are valid.
  • Questions such as "top destinations", "devices per node" or "activity per day" are joins and aggregates, which SQL does very well.
  • Transactions (all-or-nothing) are needed when one event updates four tables at once.
  • The schema is created from a plain SQL file (schema.sql), so it is visible and explainable; the Python models mirror it, rather than generating it.

For each table: what it stores, why it exists, how the application uses it, and the design decisions behind it.

1. users - who may sign in

Stores the accounts of the people who use the dashboard.

ColumnTypeNotes

How it is used. At login the backend finds the row by email (the unique index makes this one lookup), compares the password with password_hash using bcrypt, and records last_login. On every later request the user row is read again to check status and role, so disabling an account or changing a role takes effect immediately. The Users page (admin only) creates, edits and disables rows.

Why it looks like this. Users are people, not network data, so there is no foreign key to the monitoring tables. Accounts are disabled, not deleted, so history of who did what is not lost, and the application refuses to disable or demote the last active administrator so nobody can lock everyone out. The ENUM columns let MySQL reject any role or status that is not on the list.

2. nodes - authorized observation points

Stores each place where monitoring is authorized: a computer lab, the library, an office, or "this PC".

ColumnTypeNotes

How it is used. The Nodes page (admin) adds, edits and disables nodes. When an event arrives, the node found through the API key is locked; if its status is INACTIVE the event is refused with 403, and otherwise its last_seen moves forward. The dashboard's "Active nodes" figure counts rows with status ACTIVE, and the reports group activity by node.

Why it looks like this. A node is the parent of devices and keys, which gives every event a clear origin. Nodes are never deleted (history refers to them); they are set to INACTIVE instead, which also acts as an off switch for a collector.

3. devices - the machines being observed

Stores one row per logical device seen by a node.

ColumnTypeNotes

node_idBIGINT UNSIGNEDFK to nodes, ON DELETE RESTRICT, ON UPDATE CASCADE
device_identifierVARCHAR(100)The logical identity (for example PC-LAB-A-001), unique within a node

Constraints. UNIQUE (node_id, device_identifier) means a device name cannot repeat inside one node. UNIQUE (node_id, device_id) looks redundant (device_id is already unique) but is required: it is the target of the composite foreign key from network_history (Section 7.4).

How it is used. Devices are created automatically by the first event that mentions them: the service looks for node_id + device_identifier and inserts a row if none exists. Later events update last_seen and the current IP. The Devices page lists them with search (by name, IP, hostname) and filters (node, status); the device detail page shows the history of that one device.

Why it looks like this. The identity is the identifier, not the IP address, because IPs change (DHCP). If a laptop gets a new address, it stays the same device with one continuous history rather than becoming a stranger.

4. destinations - where traffic went

Stores each distinct place that was reached, once, no matter how many devices or events refer to it.

ColumnTypeNotes
destination_idBIGINT UNSIGNEDPrimary key
ip_addressVARCHAR(45)Destination IP (IPv4 or IPv6)
domainVARCHAR(255) NULLName when known; NULL when no name was observed; indexed
domain_keyVARCHAR(255) GENERATEDCOALESCE(domain, ''), STORED. Internal helper, never shown to users
categoryENUM(SEARCH, SOCIAL, DEVELOPMENT, EDUCATION, VIDEO, CLOUD, OTHER, UNKNOWN)Descriptive label; default UNKNOWN; indexed
first_seen, last_seen, created_at, updated_atDATETIMElast_seen indexed

The NULL problem and the generated column. The identity of a destination is ip_address + domain, and domain may be NULL. In MySQL a UNIQUE index allows many rows with NULL, so UNIQUE(ip_address, domain) would allow (203.0.113.50, NULL) to be inserted again and again. The generated column turns NULL into an empty string, and UNIQUE (ip_address, domain_key) then works for every case while domain itself stays truly NULL.

How it is used. On each event the service looks up ip_address + domain_key and reuses the row or creates it. It powers the Destinations page, the destination investigation page (total events, unique devices, nodes that saw it, devices that accessed it), the "top destinations" chart and the category breakdown.

Why it looks like this. Storing each destination once avoids repeating the same name and IP in millions of history rows. The category is application metadata for readability and is explicitly not a security verdict.

5. collector_api_keys - how collectors prove who they are

Stores the credentials that collectors use, one or more per node.

ColumnTypeNotes
api_key_idBIGINT UNSIGNEDPrimary key
node_idBIGINT UNSIGNEDFK to nodes, RESTRICT; the node this key speaks for
key_nameVARCHAR(100)A label such as "local collector"
key_hashVARCHAR(255)UNIQUE; SHA-256 of the key. The key itself is never stored
statusENUM('ACTIVE','REVOKED')Revoking = changing this value
created_at, last_used_at, revoked_atDATETIMElast_used_at is updated on each authenticated use

How it is used. For each event the backend hashes the X-API-Key header and finds the row through the unique index on key_hash. If the row exists and is ACTIVE, node_id tells the backend which node the event belongs to. A helper script (backend/create_collector_key.py) creates a node and key and prints the key once.

Why it looks like this. A separate table lets a node have several keys (rotation) and lets a key be revoked without deleting anything. Hashing means a leaked database does not leak working keys. A fast SHA-256 is appropriate here (unlike for passwords) because keys are long random secrets, and a fast, repeatable hash is what allows a lookup by hash. The key is bound to the node, which is why a collector can never write events for another node.

6. network_history - the events (the central table)

Stores one row per accepted event: this device, seen by this node, reached this destination, at this time.

ColumnTypeNotes

How it is used. Everything the dashboard shows is computed from this table: the recent-activity table, the activity charts, the history search page, device and destination histories, node activity and all four reports. The duplicate check queries it by device and destination within a time window.

Why it looks like this. It is a "tall and narrow" table of ids and a time, so adding millions of rows stays cheap. It deliberately stores no names or addresses: those are reached through joins (Section 7.6). Protocol and ports describe this one connection (every connection has its own ephemeral source port), so they belong on the event row, not on devices or destinations. They are nullable because not every collector can observe them; older rows simply show a dash.

7.4 Foreign keys, and the composite key that prevents impossible events

network_history has four foreign keys, all ON UPDATE CASCADE ON DELETE RESTRICT:

  1. device_id → devices(device_id)
  2. node_id → nodes(node_id)
  3. destination_id → destinations(destination_id)
  4. (node_id, device_id) → devices(node_id, device_id) (composite)

The first three only prove each id exists. They would still allow a contradiction: an event saying device 7 was seen by node 2 when device 7 actually belongs to node 1. The composite key closes that gap, because MySQL must find a devices row with that exact node and device together. This is why devices carries the extra UNIQUE (node_id, device_id): a foreign key needs a unique target.

Attempted eventResult
device_id = 7, node_id = 1 (device 7 belongs to node 1)accepted
device_id = 7, node_id = 2 (device 7 does not belong to node 2)rejected by MySQL: foreign key violation

The application also checks this, but the database enforces it even if some future code forgets to.

7.6 Normalization: why the history table holds only ids

The schema is designed to about Third Normal Form (3NF): every fact is stored in exactly one place.

  • 1NF: every column holds a single value; there are no lists inside a cell.
  • 2NF: every table has a single-column primary key, so no column can depend on only part of a key.
  • 3NF: a column depends on the key and nothing but the key. For example the node's name is not copied into devices or network_history, because it depends on the node, not on the device or the event.

A deliberate exception

last_seen on nodes, devices and destinations is technically derivable from MAX(observed_at) in the history. It is stored anyway (and updated in the same transaction as the event) so that lists such as "devices, most recently active first" do not need an expensive aggregate over the whole history. This is a conscious, documented trade-off of a little redundancy for speed.

7.7 Deletion policy: history is never lost by accident

Every foreign key uses ON DELETE RESTRICT. MySQL will refuse to delete a node that still has devices, keys or history, and refuse to delete a device or destination that events refer to. There is no cascade that could silently wipe history. Instead of deleting, the application uses statuses (ACTIVE, INACTIVE, OFFLINE, DISABLED, REVOKED). Reports and investigations therefore always have the full record.

7.8 Transactions and integrity

Storing one event changes several rows: the new history row, the last_seen of the device, destination and node, the key's last_used_at, and possibly a new device or destination row. They are performed in one transaction: either every change is committed together or, on any error, none is. This is the Atomicity and Consistency of ACID in practice. The locking reads give Isolation between simultaneous events, and InnoDB's log gives Durability.

MechanismWhat it guarantees
Primary keysEvery row is uniquely identifiable
Foreign keys (incl. composite)No event can point at something that does not exist, or at a device from the wrong node
UNIQUE constraintsNo duplicate emails, node codes, device identifiers per node, destinations, or key hashes
NOT NULL, ENUMRequired values exist, and statuses and roles come from a fixed list
Transactions + locking readsAll-or-nothing writes; no race between simultaneous events
ON DELETE RESTRICTNo accidental loss of history

7.10 Example queries (from queries.sql)

Recent activity: a four-table JOIN

SELECT h.observed_at, dv.device_identifier, n.node_name,
       d.ip_address AS destination_ip, d.domain
FROM network_history h
JOIN devices dv      ON dv.device_id      = h.device_id
JOIN nodes n         ON n.node_id         = h.node_id
JOIN destinations d  ON d.destination_id  = h.destination_id
ORDER BY h.observed_at DESC
LIMIT 20;

This one query reassembles names from ids. It is what the dashboard's "Recent network activity" table uses (with a LIMIT).

Most visited destinations: GROUP BY and HAVING

SELECT d.domain, COUNT(*) AS visits, COUNT(DISTINCT h.device_id) AS unique_devices
FROM network_history h
JOIN destinations d ON d.destination_id = h.destination_id
GROUP BY d.destination_id, d.domain
HAVING COUNT(*) >= 50          -- only busy destinations
ORDER BY visits DESC;

Devices that never produced an event: LEFT JOIN anti-join

SELECT dv.device_identifier
FROM devices dv
LEFT JOIN network_history h ON h.device_id = dv.device_id
WHERE h.history_id IS NULL;

The duplicate check the backend runs

SELECT history_id, observed_at
FROM network_history
WHERE device_id = ? AND destination_id = ?
  AND observed_at BETWEEN (? - INTERVAL 30 SECOND) AND (? + INTERVAL 30 SECOND)
ORDER BY observed_at DESC
LIMIT 1
FOR UPDATE;

A row returned means "duplicate: do not insert". It is fast because of the index on (device_id, observed_at).

8.3 Behaviors worth knowing

  • Every data page handles three states: a loading skeleton, an empty state ("No network activity found. Try changing your filters.") and an error state with a Try again button. A missing record shows "Not found" with a link back.
  • Search and filters run on the backend. The browser sends the filters in the request; it never downloads the whole table and filters it itself. The filters are kept in the address bar, so a filtered view can be bookmarked or shared.
  • The session (token and user) is kept in the browser's local storage. A request answered with 401 ends the session and returns to the login page.
  • Role guards in the UI hide pages and buttons the user cannot use, but the backend enforces the same rules, so they are a convenience only.
  • Responsive: a persistent sidebar on desktop, a slide-in menu on phones; wide tables scroll inside their own box; the source-port column hides on narrow screens. Verified at 1280, 768 and 375 pixels wide.
  • Honest display: a missing value is a dash, a destination without a name shows its IP marked "(unresolved)", and nothing is invented.

9Security

AreaWhat was done
PasswordsHashed with bcrypt (work factor 12, never below 10). Never stored, returned or logged. Unknown emails take the same time as wrong passwords, and the message is the same for both.
Login tokensJWT signed with HS256 (the algorithm is fixed, so a token cannot choose its own). The token carries only the user id and an expiry (60 minutes); role and status are re-read from the database on every request. The server refuses to start without a random secret of at least 32 characters, and rejects placeholder values.
RolesADMIN and ANALYST are enforced by the backend on every protected route (401 not signed in, 403 not allowed). The last active admin cannot be disabled or demoted.
Collector keysRandom secrets, stored only as SHA-256 hashes, tied to one node, revocable. The node always comes from the key, never from the payload.
SQL injectionAll queries go through SQLAlchemy with bound parameters. Tests send injection strings through every search box, the login form and URL ids. SQL errors never echo bound values.
Input validationPydantic checks types, lengths, IP formats, port ranges and protocol values; unknown fields are rejected; page size and page number are capped.
Browser protectionCORS allows only the configured frontend origin, without credentials. Responses carry X-Content-Type-Options, X-Frame-Options, Referrer-Policy and Cache-Control: no-store. React escapes all displayed data, and no raw HTML is injected.
Errors and loggingNo stack traces or internals reach the client; validation errors do not repeat the submitted input.
ExposureInteractive API docs can be switched off for deployment. The database health check needs a login. Secrets live in environment variables and .env files that are not committed.
Privacy scopeMetadata only. The collectors contain no packet capture, scanning, discovery, payload or process-name collection, and the local collector sees only the computer it runs on.
DependenciesChecked with pip-audit and npm audit during the final audit (no known vulnerabilities at that time).

10Testing and quality

Backend tests

Run against real MySQL inside a transaction that is rolled back, so the demo data is never changed. They cover login and roles, every endpoint, ingestion and the 30-second rule (including races and rollbacks), foreign keys, and security hardening.

Collector tests

The Windows connection table is replaced by hand-built bytes, so tests never depend on real traffic. They cover parsing, new-versus-seen detection, domain choice, retries, bad data and Ctrl+C.

Frontend tests

A fake fetch stands in for the backend. Tests cover login, route guards, every page, loading, empty, error and not-found states, and fail on any unexpected network call or console warning.

In addition, the frontend passes lint (oxlint) and builds for production without errors. Code size at the end: about 2,300 lines of backend application code, 1,000 of collector code and 3,950 of frontend code, plus roughly 6,600 lines of tests and 1,800 of SQL.

12Limitations and future work

12.1 Known limitations

  • The real collector sees one computer, TCP only. Phones, other laptops and router traffic are invisible to it, and UDP/QUIC visits (common for large video and search sites) are not captured. Browsers that use their own DNS can leave destinations without a name.
  • No login rate limiting. Repeated password guesses are only slowed by bcrypt itself; a limiter should be added at the web server in a real deployment.
  • No audit log of who did what (only unhandled errors are logged).
  • Tokens cannot be revoked early except by disabling the user, and they live in browser storage, so a Content-Security-Policy should be added at the web server in production.
  • API keys are created with a script (or in the database); there is no screen for managing them.
  • Times are naive local server time, with no time-zone conversion.
  • Simulated and real events look the same in the history; only the node tells them apart.

12.2 Ideas for the future

  • A DNS-based collector (for example reading a DNS server's log on a home network the owner controls) to see names from many devices without packet capture.
  • Authorized gateway observation for UDP and QUIC metadata, kept strictly to headers and never contents.
  • Alerts for unusual behavior (for example a burst of connections) as a separate, clearly scoped feature.
  • A screen for managing collector keys, an audit log, login rate limiting, HTTPS deployment, and a marker column for simulated events.
